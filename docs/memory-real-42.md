# 实际42篇PDF：本地内存与保护检查

2026-10-12；macOS arm64、Python 3.12。只读真实任务中的42个文件；所有任务副本、索引、证据包写入临时目录并自动清理。无API客户实例、无模型调用、未修改用户设置、任务或PDF。

## 已落地

- 模型请求前先统计全部PDF页数／字符，再逐篇解析到磁盘；已有缓存也预检。任何超限或解析错误发生在这阶段时，模型调用为零，并指出文件与拆分建议。
- 移除整批40万字符中断。每篇最多30万PDF字符、200页、15MB；单次50篇不变。30万基于本批最大274,746字符和本机峰值测量，小幅留余量，不承诺跨平台内存硬上限。
- 坐标索引逐篇写入完整schema-1 JSON，偏移侧文件支持随机读取；至多缓存一篇完整索引，源指纹等摘要读取不加载坐标。模型仍只读当前引用来源并按65,000字符预算拆分／合并。
- 旧JSON保持兼容；缺失或失效侧文件回退旧格式读取。这种首次兼容读取仍可能使用较大内存，不能把新文件的按需内存结果套用到所有旧备份。

## 实测

原始数据：`benchmark-real-42.json`；规模统计：`real-42-scale.json`。

| 项目 | 结果 |
|---|---:|
| 完整解析材料 | 42篇／511页 |
| 总PDF字符 | 2,674,635 |
| 单篇最多字符／页数 | 274,746／39 |
| 当前任务已匹配来源 | 25篇 |
| 原文坐标核验 | 26处来源关系 |
| 完整本地流程峰值RSS | 457.33 MB |
| 本地解析、包构建和坐标验证 | 16.83秒 |
| 临时缓存＋证据包等磁盘 | 354.00 MB |

对照是相同文件顺序的旧式累积索引模拟，在第8篇累积473,453字符触发40万保护，峰值300.25 MB；它没有完成42篇，不能直接与新流程计算降幅或视作旧完整业务耗时。模型请求、返回结果、浏览器内存、长时间连续任务均不在此实测范围。坐标核验使用程序从实际PDF选取原句，不验证语义支持判断。

建议先20—30篇普通论文、较长PDF减少数量；42篇本机通过不代表任何42篇都安全。篇数用于操作建议，实际保护以每篇字符／页数及请求文本预算为准。跨平台正式数量建议和安装包更新仍为发布待办。

复现（替换为用户自己的任务路径）：

```sh
python scripts/benchmark_real_materials.py --task /path/to/task.json
```

脚本每种模式使用独立子进程，读取本地PDF并在临时目录操作；没有真实模型验收能力。

回归：238项Python测试通过，覆盖最后一篇超限前零API调用、缓存不能绕过预检、超过40万的包构建、单篇缓存替换、失效偏移兼容读取、旧报告／备份恢复与证据指纹校验。2026-10-13已构建0.4.6 macOS arm64测试包；新包需按冻结应用冒烟流程验收。
